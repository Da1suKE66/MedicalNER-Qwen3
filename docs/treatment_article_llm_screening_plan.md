# 治疗相关文章的 LLM 筛选与高质量知识图谱生成方案

## 1. 文档状态与目标

本文档只描述方案，不包含实现代码，也不代表已经开始调用外部 LLM。

当前原始语料位于：

```text
data/treatment_related_articles/articles.json
```

该文件约 419 MB，包含 180,373 条带标题和摘要的文章记录：

| 来源 | 记录数 |
| --- | ---: |
| PubMed | 61,259 |
| Embase | 118,755 |
| Cochrane | 359 |
| 合计 | 180,373 |

目标不是直接让高级 LLM 为全部摘要生成知识图谱，而是建立一个可恢复、可审计、成本可控的两阶段流程：

1. 使用本地规则和成本较低的 LLM 判断哪些摘要适合生成知识图谱；
2. 只把高质量候选交给能力更强、成本更高的 LLM 生成知识图谱；
3. 对生成的每条关系执行原文证据核验；
4. 最终形成一批适合训练 MedicalNER/Qwen3 的高置信度知识图谱数据。

## 2. 核心原则

文章的学术质量和知识图谱可抽取性不是同一件事。

一篇研究可能具有较高学术价值，但摘要没有给出完整结果，或者其信息无法映射到目标图谱的实体和关系，此时不适合仅依据摘要生成训练数据。反过来，一篇普通临床研究只要清楚描述了人群、干预、对照和结局，也可能提供多条可靠关系。

因此，筛选时应回答：

> 该摘要是否明确提供了至少一条与目标图谱 schema 匹配，并且能够由摘要原文直接支持的医学关系？

整个流程遵循以下原则：

1. 不使用模型自身的医学常识补全摘要中没有出现的事实；
2. 每条保留的关系必须绑定原文证据；
3. 研究中观察到有效，不等同于临床指南中的一线推荐；
4. 研究相关性、证据质量和关系可抽取性分别评分，不互相替代；
5. 所有 accept、review 和 reject 决定都保留原因和来源信息；
6. 先用小规模样本验证筛选标准，再处理完整语料库；
7. 付费 API 默认不自动重试，已完成记录不能重复付费请求。

## 3. 先确定目标知识图谱

筛选开始前必须先确定最终知识图谱的使用范围。否则，同一篇文章可能在一种 schema 下适合，在另一种 schema 下不适合。

### 3.1 现有实体和关系体系的限制

现有 Gemini 示例脚本主要使用以下实体类型：

- Disease
- Symptom
- Diagnostic Criteria
- Interview Tool
- Patient Information
- Medication
- Communication Method
- Risk Information

这套体系适合精神疾病诊疗、症状和问诊知识，但不足以完整表达临床研究证据。

例如，摘要可能只证明：

> 在特定患者群体中，药物 A 相比安慰剂降低了某项结局。

不能据此直接生成：

```text
药物 A --first_line_for--> 疾病 B
```

“在研究中表现有效”和“被临床指南推荐为一线治疗”属于不同强度的结论。如果忽略研究设计、人群、对照和结局，生成的知识图谱容易发生医学语义扩大。

### 3.2 推荐的证据型中间层

建议先构建一层“治疗证据知识图谱”，再将其中符合条件的知识投影到现有 MedicalNER schema。中间层至少应能够表达：

- Disease
- Intervention
- Medication
- Population
- Comparator
- Outcome
- Adverse Event
- Dosage
- Study
- Evidence
- Effect Direction
- Evidence Strength

典型关系可以包括：

- intervention evaluated_for disease
- intervention compared_with comparator
- intervention improves outcome
- intervention worsens outcome
- intervention has_adverse_event adverse_event
- finding observed_in population
- finding supported_by study
- medication administered_at dosage

每条结论还应保留：

- 研究设计；
- 患者人群；
- 干预和对照；
- 结局；
- 效应方向；
- 效应量、置信区间或统计值（摘要明确提供时）；
- 证据句；
- 来源记录和 DOI；
- 模型置信度；
- 是否需要人工复核。

如果项目决定继续严格使用现有 schema，也应先列出允许筛选模型识别的实体类型、关系类型和 domain/range，避免筛选阶段和生成阶段使用不同标准。

## 4. “适合生成知识图谱”的评分标准

建议使用 10 分制，同时设置不可绕过的证据门槛。

| 维度 | 分值 | 判断内容 |
| --- | ---: | --- |
| 主题相关性 | 0–2 | 是否直接讨论治疗、干预、用药、疗效或安全性 |
| 关系可抽取性 | 0–3 | 是否明确出现两个实体及二者之间的目标关系 |
| 证据质量 | 0–2 | 研究设计和结论的证据强度 |
| 摘要完整性 | 0–2 | 是否包含足够的人群、干预、结局和结果信息 |
| 信息密度 | 0–1 | 是否能够稳定产生一条以上的有用关系 |

建议的初始判定阈值：

| 总分 | 判定 | 后续处理 |
| ---: | --- | --- |
| 8–10 | accept | 进入高级 LLM 生成阶段 |
| 5–7 | review | 进入待复核池 |
| 0–4 | reject | 暂不用于生成 |

无论总分多少，以下硬门槛必须满足才能进入 accept：

1. 至少有一条目标关系；
2. 关系两端实体均在摘要中明确出现；
3. 模型能够返回直接支持该关系的原文证据句；
4. 结论没有超出原文的证据强度；
5. 摘要不是仅介绍研究计划而没有结果。

## 5. 文章类型及初始优先级

文章类型不能单独决定是否保留，但可以作为证据质量和处理顺序的参考。

### 5.1 优先处理

- 临床指南或共识中明确给出治疗建议的摘要；
- 有明确结果的系统综述和 Meta-analysis；
- 有明确干预、对照和结局的随机对照试验；
- 明确报告疗效、安全性或不良反应的临床研究；
- 明确报告特定人群治疗差异的研究；
- 明确报告药物剂量、相互作用或禁忌证的研究。

### 5.2 进入 review 池

- 观察性研究；
- 真实世界研究；
- 样本量较小但关系描述清楚的研究；
- 结论方向明确但缺少效应量的研究；
- 摘要可能被截断或缺少部分上下文的研究；
- 只包含一条低密度关系但主题高度相关的研究。

### 5.3 通常不进入高级生成阶段

- 只有研究背景和目标，没有实际结果的 protocol；
- 会议通知、社论、评论或行政文本；
- 仅讨论患病率但没有治疗相关知识的文章；
- 只描述分子或动物实验，而项目目标限定为临床知识的文章；
- 摘要无法确定干预对象、作用方向或患者人群；
- 主要结论需要依赖全文才能判断的文章；
- 与目标疾病领域或目标 schema 无关的文章。

研究方案不应永久删除，可单独标记为 `protocol_without_results`。如果以后需要构建临床试验图谱，可以重新使用。

## 6. 分层筛选流程

### 6.1 第一层：本地规则预筛选

该阶段不调用外部 LLM，目标是排除确定无效的数据并减少重复付费。

主要任务包括：

1. 校验记录必须包含 `source`、`title` 和 `abstract`；
2. 识别损坏、乱码、明显截断或非自然语言摘要；
3. 使用 DOI、规范化标题和近似标题进行跨来源去重；
4. 标记 protocol、会议摘要、社论和评论等文章类型；
5. 标记明显不属于目标疾病或治疗范围的记录；
6. 记录摘要长度、来源和可用标识符，供分层抽样使用。

不建议仅按摘要长度直接拒绝：

- 短摘要可能包含非常明确的药物—疾病关系；
- 长摘要可能包含大量背景，却没有实际结果。

跨来源重复时，建议保留内容更完整的版本，同时保留全部来源和重复映射。Cochrane 综述和其引用的原始 RCT 不属于简单重复，二者代表不同证据层级，可以同时保留。

### 6.2 第二层：低成本 LLM 结构化初筛

这一阶段只做分类，不生成完整知识图谱，也不要求输出长推理过程。

每条筛选结果至少包含：

| 字段 | 说明 |
| --- | --- |
| record_id | 与原始文章稳定对齐的唯一标识 |
| decision | accept、review 或 reject |
| total_score | 0–10 的总分 |
| dimension_scores | 各评分维度的独立分数 |
| article_type | RCT、systematic_review、protocol 等 |
| treatment_relevance | 是否直接讨论治疗知识 |
| evidence_level | 摘要能够支持的证据等级 |
| supported_entity_types | 摘要明确支持的实体类型 |
| supported_relation_types | 摘要明确支持的关系类型 |
| estimated_fact_count | 预计可抽取的可靠关系数量 |
| evidence_spans | 支持筛选决定的原文片段 |
| rejection_reasons | 固定枚举的拒绝原因 |
| requires_full_text | 是否必须查看全文后才能判断 |
| model_metadata | 模型、请求时间和响应版本 |

建议使用固定拒绝原因：

- `not_treatment_related`
- `protocol_without_results`
- `background_only`
- `no_supported_relation`
- `insufficient_specificity`
- `nonclinical_out_of_scope`
- `abstract_incomplete`
- `duplicate_record`
- `unsupported_language`
- `response_invalid`

筛选模型不应输出长 Chain-of-Thought。简短判定理由、维度分数和证据片段已经足够进行审核，并能降低 token 成本和格式不稳定性。

### 6.3 第三层：候选集去冗余与覆盖度采样

如果只按总分从高到低选择，候选集可能集中在少数热门疾病和药物上。进入高级生成阶段前，应按以下维度检查覆盖度：

- 疾病；
- 药物或干预；
- 关系类型；
- 研究类型；
- 患者人群；
- 数据来源；
- 证据等级；
- 安全性、疗效、剂量和相互作用等知识主题。

对于高度相似的候选，可优先保留：

1. 结论和限定条件更完整的版本；
2. 证据级别更高的研究；
3. 样本量更大且结果更明确的研究；
4. 能提供更多目标关系的研究；
5. 有 DOI、PMID 或其他稳定来源标识的研究。

候选集不应只有高频疾病。可以为低频但重要的疾病、关系类型和人群设置最低配额，避免最终训练数据分布过窄。

### 6.4 第四层：高级 LLM 生成知识图谱

只有 accept 文章和经过确认的 review 文章进入这一阶段。

高级模型必须遵守：

1. 只使用标题和摘要中出现的信息；
2. 不调用自身医学常识补充缺失事实；
3. 每个实体必须对应可定位的原文 span；
4. 每条关系必须绑定支持它的原文证据；
5. 明确保留人群、对照、结局和证据强度；
6. 不把相关性改写为因果性；
7. 不把试验结果改写为临床指南推荐；
8. 信息不足时返回空关系或人工复核标记，而不是猜测。

生成结果应尽量与项目现有 Schema v2 的严格验证原则一致，包括实体/关系 domain-range、证据原文、证据偏移和来源追踪。

### 6.5 第五层：独立核验

生成模型完成后，需要由独立核验步骤逐条检查：

- 头实体是否在原文中；
- 尾实体是否在原文中；
- 关系是否被证据句直接支持；
- 关系方向是否正确；
- 是否遗漏否定词、不确定性或比较条件；
- 是否错误扩大研究结论；
- 是否违反 schema 的 domain/range；
- 是否与同一摘要中的其他关系矛盾。

建议将核验结果分为：

- `verified`
- `needs_review`
- `rejected`

只有 `verified` 关系才能进入最终训练数据。筛选模型、生成模型和核验模型的职责应分离；不能把“生成成功”当作“关系正确”。

## 7. 小规模试验方案

不应立即处理全部 180,373 篇文章。第一轮建议建立约 500 篇分层样本：

| 来源 | 建议样本数 |
| --- | ---: |
| PubMed | 200 |
| Embase | 200 |
| Cochrane | 100 |

样本还应覆盖：

- 短、中、长摘要；
- 不同文章类型；
- 不同疾病和治疗主题；
- 有结果和无结果的摘要；
- DOI 完整和 DOI 缺失的记录；
- 可能重复和明显不重复的记录。

推荐的验证顺序：

1. 人工为约 100–200 篇文章标注 accept、review 或 reject；
2. 记录人工认为可抽取的实体类型、关系类型和证据句；
3. 先运行一个约 20 篇的代表性 canary；
4. 确认模型理解评分标准和输出格式；
5. 扩大到 500 篇试验集；
6. 统计误判、漏判、解析失败和预计总成本；
7. 调整规则、评分阈值和提示词；
8. 达到质量门槛后才开始完整语料筛选。

建议的初始质量门槛：

| 指标 | 建议目标 |
| --- | ---: |
| accept 集人工精确率 | ≥ 90% |
| reject 集高价值文章漏判率 | ≤ 10% |
| 结构化响应解析成功率 | ≥ 99% |
| accept 文章至少含一条直接证据关系 | ≥ 95% |
| 已完成记录重复付费请求 | 0 |

这些数值是项目门槛，不是模型能力的预先保证。如果没有达到，应继续调整筛选标准，而不是直接扩大处理规模。

## 8. 成本与恢复设计

现有 `test_gemini_chat_completion.py` 中以下设计可以继续参考：

- OpenAI-compatible API 调用方式；
- 成功结果立即保存；
- 已完成记录自动跳过；
- 原始响应和规范化结果同时保留；
- 失败记录单独记录；
- 本地修复可恢复的格式差异；
- 默认不自动重试付费请求。

不应直接沿用：

- 面向知识图谱生成的原始 prompt；
- 强制输出 `<think>` 的要求；
- 针对 22 条数据设计的固定假设；
- 将现有八类实体作为所有治疗文献的唯一筛选标准；
- 每次失败后重新请求整个批次。

完整语料筛选时，可以将多个带稳定 ID 的摘要放入同一请求以降低固定开销，但每批大小应根据摘要长度和模型上下文动态控制。模型必须原样返回每个 `record_id`，不能依赖数组顺序对齐。

如果某批响应不完整：

1. 先保存原始响应；
2. 尝试从原始响应本地恢复已完成记录；
3. 只将没有有效结果的 ID 标记为 unresolved；
4. 不自动重新付费请求；
5. 经人工确认后，只重新请求 unresolved 记录。

建议保留一个统一的运行账本，记录：

- record_id；
- 输入哈希；
- prompt 版本；
- schema 版本；
- 模型名称；
- 请求状态；
- 响应哈希；
- token 用量；
- 解析状态；
- 失败原因；
- 是否已经付费请求。

## 9. 建议产物

为避免生成十万个零散文件，建议工作阶段使用一个可追加、可恢复的状态存储，并输出少量汇总文件：

```text
data/treatment_related_articles/
├── articles.json
├── article_screening_gold_sample.json
├── article_screening_results.jsonl
├── article_screening_summary.json
├── article_screening_accept.json
├── article_screening_review.json
├── article_screening_reject_index.jsonl
├── treatment_kg_generated.jsonl
├── treatment_kg_verified.json
└── treatment_kg_generation_report.json
```

建议含义：

- `article_screening_gold_sample.json`：人工标注的小规模金标准；
- `article_screening_results.jsonl`：全部筛选决定和审计字段；
- `article_screening_summary.json`：来源、文章类型、分数和拒绝原因统计；
- `article_screening_accept.json`：高级 LLM 的候选输入；
- `article_screening_review.json`：需要人工或第二模型复核的记录；
- `article_screening_reject_index.jsonl`：被拒绝记录的 ID、原因和分数；
- `treatment_kg_generated.jsonl`：高级模型原始生成结果；
- `treatment_kg_verified.json`：通过证据核验的最终图谱数据；
- `treatment_kg_generation_report.json`：生成、核验、失败和成本报告。

JSONL 适合大规模任务断点恢复，最终训练和交付数据仍可合并为单个 JSON 文件。

## 10. 安全与外部数据边界

摘要会被发送给第三方模型服务，因此开始完整任务前需要确认：

1. 数据所有者允许将标题和摘要发送到所选 API；
2. API 日志和供应商的数据保留政策可以接受；
3. 输入中不包含不应外发的敏感数据；
4. API key 只从环境变量或未纳入 Git 的 `.env` 文件加载；
5. 请求和报告中不记录完整 API key。

当前参考脚本中存在明文 API key。正式运行任何新任务前，应先轮换该 key，并移除代码中的明文凭据。

## 11. 推荐实施顺序

1. 明确最终采用现有 Schema v2，还是新增治疗证据中间层；
2. 固定允许的实体、关系、domain/range 和证据要求；
3. 人工标注 100–200 篇筛选金标准；
4. 构建约 500 篇的分层试验集；
5. 运行约 20 篇 canary，人工检查模型判定；
6. 验证完整 500 篇试验并调整阈值；
7. 评估完整语料的预计 accept 比例和 API 成本；
8. 执行本地预筛选和跨来源去重；
9. 使用低成本模型完成全量结构化初筛；
10. 对 accept 集执行覆盖度采样和去冗余；
11. 使用高级模型生成证据绑定的知识图谱；
12. 执行独立关系核验；
13. 只将通过核验的数据转换成训练格式；
14. 冻结最终数据、schema、prompt、模型版本和审计报告。

## 12. 开始实现前需要确认的决策

正式编写筛选脚本前，需要明确以下问题：

1. 目标是否只覆盖精神疾病治疗，还是覆盖全部治疗相关文章；
2. 是否继续严格使用当前八类实体；
3. 是否接受新增 Population、Comparator、Outcome、Study 等证据型实体；
4. protocol 和动物实验是否完全排除；
5. 是否允许没有效应量但结论明确的研究进入 accept；
6. 最终希望保留多少篇文章，或者可接受的 API 预算是多少；
7. 筛选阶段使用本地模型、低成本 API，还是二者结合；
8. review 池由人工复核还是由第二个模型复核；
9. 最终训练目标是否要求保留 CoT；
10. 第三方 API 的数据外发权限是否已经确认。

在这些决策确定之前，不建议直接对完整语料发起 LLM 请求。
