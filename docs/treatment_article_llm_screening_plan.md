# 20 万篇治疗相关摘要的前沿 LLM 知识图谱处理方案

## 1. 文档状态

本文档是方案设计，不包含实现代码，也不代表已经开始调用外部 API。

更新后的方案不再使用“低成本通用 LLM 先筛选、高级 LLM 再抽取”的主线。原因是筛选本身就要求模型理解研究设计、证据强度、医学实体和目标关系；能力不足的模型容易在第一步误删真正有价值的摘要，而且筛选调用还会重复消耗全部摘要的输入 token。

本文推荐：

> 让前沿模型对每篇去重后的摘要执行一次“可拒绝的知识图谱抽取（extract-or-abstain）”。能够抽取出有原文证据的关系时返回简洁图谱；不能可靠抽取时返回空结果。筛选由抽取结果自然产生，而不是额外建立一个语义分类器。

随后使用确定性规则校验全部结果，再由前沿模型验证已经产生的关系，只把争议项交给更强的推理模型裁决。

## 2. 数据现状与目标

原始语料位于：

```text
data/treatment_related_articles/articles.json
```

文件约 419 MB，包含 180,373 条有标题和摘要的记录：

| 来源 | 记录数 |
| --- | ---: |
| PubMed | 61,259 |
| Embase | 118,755 |
| Cochrane | 359 |
| 合计 | 180,373 |

最终目标不是机械地产生 180,373 条训练样本，而是：

1. 让所有去重后的摘要都有一次由前沿模型完成的抽取机会；
2. 对信息不足的摘要允许模型明确放弃；
3. 所有实体和关系均绑定摘要原文证据；
4. 排除格式正确但医学语义不受原文支持的关系；
5. 去除图谱层面的重复知识并控制主题分布；
6. 只把通过验证的数据转换为最终训练格式。

## 3. 总体架构

```text
articles.json
    |
    v
确定性清洗与跨来源去重
    |
    v
前沿模型：extract-or-abstain，一次处理全部唯一摘要
    |
    +--> 空图谱/证据不足 ------> 分层抽查漏检率
    |
    v
本地严格校验：JSON、schema、证据、引用、重复
    |
    v
前沿模型：逐关系简洁验证
    |
    +--> 一致通过 ------------> verified
    |
    +--> 不支持 --------------> rejected
    |
    +--> 不确定/模型分歧 -----> 推理模型裁决
    |
    v
图谱去重、覆盖度控制与训练数据生成
    |
    v
仅对最终保留样本生成需要的 CoT 或教学解释
```

这套设计中，前沿模型始终承担医学语义判断。非 LLM 步骤只处理能够确定验证的结构事实，不负责判断复杂医学价值。

## 4. 为什么不再单独做低成本 LLM 筛选

单独筛选存在四个问题：

1. **任务难度没有真正降低。** 判断一篇摘要是否适合抽取，需要理解其疾病、人群、干预、结局、证据强度和目标 schema。
2. **会发生不可恢复的误删。** 被筛选模型判为 reject 的摘要不会再交给高级模型，漏检会直接损失知识。
3. **重复读取全部语料。** 筛选模型和抽取模型都要读取摘要，增加输入 token 和调度复杂度。
4. **质量分不如实际图谱可验证。** “文章质量 8 分”难以审计，而“关系 R 是否由证据句 E 支持”可以严格验证。

因此，不再先预测“值不值得抽取”，而是让前沿模型实际尝试抽取。输出为空就是筛选结果，输出非空则进入验证。

## 5. 第零阶段：只做确定性清洗与去重

这一阶段不能用简单关键词决定医学相关性，只做不会依赖复杂语义判断的操作。

### 5.1 数据校验

- 每条记录生成稳定的 `record_id`；
- 保留 `source`、`title`、`abstract`、DOI 和原始索引；
- 记录规范化前后的文本哈希；
- 检查空文本、损坏字符、异常编码和明显重复字段；
- 使用实际调用模型的 tokenizer 统计 token，而不是按文件字节数估算计费量。

### 5.2 跨来源去重

当前语料的历史抽取主要在单个来源内部去重，因此全量调用前还应检查跨 PubMed、Embase 和 Cochrane 的重复记录。

建议按以下顺序建立重复簇：

1. DOI 完全相同；
2. 规范化标题完全相同；
3. 清洗后摘要完全相同；
4. 标题和摘要均高度近似的记录。

同一重复簇只将最完整的摘要发送给模型，但必须保留其他来源的 provenance，并在最终结果中把一个图谱映射回全部来源记录。

系统综述和其中引用的原始 RCT 不是简单重复，不能因为讨论同一治疗主题就合并。

## 6. 第一阶段：前沿模型直接执行 extract-or-abstain

### 6.1 一次请求同时完成抽取和筛选

现有“提取知识图谱的 prompt”可以继续作为医学知识和 schema 约束的基础，但应增加明确的拒绝能力：

- 摘要支持目标关系时，返回实体、关系和证据；
- 摘要没有足够信息时，返回合法的空实体/空关系结果；
- 不允许为了满足输出数量而猜测关系；
- 不允许用模型自身知识补全摘要没有陈述的结论；
- 不把试验中的有效性扩大为临床指南推荐；
- 不把相关性改写为因果性；
- 不遗漏否定、不确定性、比较对象和人群限定。

“空图谱”不是请求失败，而是一个合法结果。这样就不再需要独立的 accept/reject 模型。

### 6.2 第一遍输出必须尽量简洁

第一遍处理全部语料时，只返回后续验证必需的信息：

| 字段 | 说明 |
| --- | --- |
| record_id | 与输入稳定对齐的 ID |
| extraction_status | extracted、no_supported_graph 或 uncertain |
| entities | 实体 ID、类型、规范名和原文 span |
| relations | 头实体、关系、尾实体和证据引用 |
| evidence | 原文证据文本及字符偏移 |
| qualifiers | 人群、否定、比较、剂量、效应方向等限定信息 |
| warnings | 截断、歧义、全文依赖等问题 |
| schema_version | 使用的 schema 版本 |
| prompt_version | 使用的 prompt 版本 |

第一遍不应输出：

- 长篇 Chain-of-Thought；
- 摘要复述；
- 医学背景科普；
- 对每个空结果的长解释；
- 与训练无关的自然语言包装；
- Markdown 代码块或 XML 外壳。

模型可以在内部进行推理，但第一遍只保留严格 JSON。输出越短，20 万条规模下节省的成本越明显，结构也更稳定。

### 6.3 证据是核心，不使用模糊质量分替代

每个实体必须对应摘要中的原文 span；每条关系必须指向一段能够直接支持该关系的证据。

不能仅因为实体 A 和实体 B 同时出现在摘要中，就认定它们存在目标关系。例如：

- “研究比较 A 与 B”不等于“A 优于 B”；
- “患者使用 A”不等于“A 是一线治疗”；
- “A 与 B 相关”不等于“A 导致 B”；
- “未发现显著差异”不能抽取成正向疗效关系。

与其让模型给文章打一个难以校准的 0–10 分，更适合记录实际抽取出的关系、证据和限定条件。

## 7. 前沿模型的角色分工

可以使用 DeepSeek 一类前沿模型，但不建议让同一个请求同时承担生成、复核和最终裁决。

### 7.1 主抽取模型

主抽取模型处理全部唯一摘要，重点要求：

- 医学语义能力强；
- 遵循 JSON/schema 的能力稳定；
- 支持足够的输出长度；
- 适合高并发或批量任务；
- 能稳定返回证据原文；
- 允许明确输出空图谱。

结构化抽取通常应先测试旗舰非推理模型。可见推理 token 很长的模型未必更适合全量第一遍，因为格式抽取更依赖指令遵循和证据约束，而不是输出长推理过程。

### 7.2 关系验证模型

验证模型只接收：

- 原摘要；
- 主模型抽取出的实体；
- 主模型抽取出的关系；
- 对应证据。

它不重新生成完整图谱，只对每条关系返回：

- `supported`；
- `unsupported`；
- `uncertain`；
- 必要的简短原因；
- 正确的证据位置或问题类型。

验证输出远短于重新抽取，可以使用另一前沿模型家族以降低同源错误。预算受限时，也可以先用同一供应商的另一个旗舰模型，但生成和验证 prompt 必须独立。

### 7.3 推理模型裁决

推理型前沿模型只处理以下小部分记录：

- 主抽取模型和验证模型结论不一致；
- 摘要包含复杂否定、亚组、多个比较组或多重结局；
- 证据句同时支持多个可能关系；
- 关系方向或证据强度存在歧义；
- 本地 schema 校验通过，但医学语义验证为 uncertain。

这样可以把昂贵的推理 token 集中用在真正困难的样本，而不是平均分配给全部 18 万篇摘要。

## 8. 第二阶段：本地严格校验

所有非空抽取结果先经过本地确定性校验，再发送给前沿验证模型。

校验至少包括：

1. 返回内容是否为合法 JSON；
2. 顶层字段和字段类型是否符合固定 schema；
3. 实体 ID 是否唯一；
4. 关系的头尾实体是否真实存在；
5. 实体和关系类型是否在允许集合中；
6. relation domain/range 是否正确；
7. 证据字符偏移是否能精确还原原文；
8. 证据文本是否确实来自当前摘要；
9. 是否出现跨文章引用或 record_id 错配；
10. 是否存在完全重复的实体和关系；
11. 是否存在空名称、通用占位名称或非法属性；
12. 输入哈希、prompt 版本和 schema 版本是否匹配任务清单。

本地校验只能确认结构和证据定位，不能取代医学语义验证。一个幻觉关系也可能引用摘要中的真实句子，因此非空关系仍需前沿模型复核。

格式近似正确时，应先尝试本地规范化并保存修复记录，不能直接重新付费请求。

## 9. 空图谱的漏检控制

主模型返回空图谱时，不需要全部进行第二次调用，否则会退化成双倍全量处理。但必须估计空结果中的漏检率。

建议按以下维度对空结果分层抽样：

- 来源；
- 摘要长度；
- 疾病主题；
- 文章类型；
- 是否出现药物、干预、对照和结果表述；
- 模型是否返回 `uncertain` 或 warning。

对各层抽取固定比例的空结果，交给独立前沿模型盲审。若某一层漏检明显偏高，只重新处理该层，而不是重新处理全部空结果。

这一步估计的是 extractor 的 false negative，不是简单检查 JSON 是否为空。

## 10. 如何高效地调用 18 万篇摘要

### 10.1 优先区分两种“批处理”

**供应商原生 Batch API：** 每篇摘要仍是独立请求，只是由供应商异步调度。只要所选服务支持，应优先使用，因为它不会增加跨文章污染，并且可能具有更好的吞吐或价格。

**多摘要 prompt packing：** 把多篇摘要放进同一个上下文，让模型返回按 `record_id` 对齐的结果数组。它能摊薄重复 prompt 的 token，但可能降低质量。

两者不是一回事。原生 Batch API 可以保持一篇一请求；prompt packing 必须经过质量试验后才能使用。

### 10.2 Prompt overhead 是主要优化点之一

假设：

- 唯一摘要数为 `N`；
- 固定 prompt 长度为 `P` tokens；
- 每个请求打包 `B` 篇摘要；
- 全部摘要本身共有 `A` tokens。

第一遍输入 token 约为：

```text
A + ceil(N / B) * P
```

例如固定 prompt 为 1,500 tokens、唯一摘要为 180,000 篇：

- 一篇一请求，仅重复 prompt 就约 2.7 亿 tokens；
- 八篇一请求，重复 prompt 约降至 3,375 万 tokens。

实际数字必须使用目标模型 tokenizer 对当前数据和 prompt 统计。该示例只说明：在 20 万条规模下，重复 prompt 可能比预想中更昂贵。

### 10.3 推荐的 batching 优先顺序

1. 首先确认供应商是否提供原生 Batch API；
2. 确认相同 system prompt 是否能利用 prompt caching；
3. 若没有合适的原生批处理，再测试多摘要 packing；
4. 分别比较每次 1、4、8 篇摘要的质量和成本；
5. 只选择质量没有明显下降的最大 batch；
6. 长摘要单独处理，短摘要按 token 长度动态装箱；
7. 每个输出对象必须返回显式 `record_id`，禁止依赖数组位置；
8. 同一个请求中的文章之间禁止共享实体或关系。

不建议一次打包几十或上百篇摘要。超长上下文虽然技术上可能容纳，但容易发生漏项、跨文章混淆、后部文章质量下降和响应截断。

### 10.4 Prompt caching

固定 schema、关系定义、示例和输出约束应放在完全一致的前缀中，变量部分只包含 `record_id`、标题和摘要。

如果供应商支持显式或隐式 prompt caching，可显著减少重复前缀的实际计算或计费。是否支持、如何计费以及缓存是否跨请求生效，必须以最终选定 API 的实测结果为准，不能仅根据兼容 OpenAI 请求格式推断。

### 10.5 输出 token 控制

全量任务不能让模型默认生成长解释。建议：

- 空图谱只返回最小合法 JSON；
- 非空结果只返回实体、关系、证据和限定字段；
- 设置与摘要长度相匹配的输出上限；
- 响应截断时保留原始结果并标记，不能把半个 JSON 当成功；
- CoT、教学解释和自然语言分析推迟到最终数据集阶段。

### 10.6 并发和分片

建议将任务逻辑分成固定分片，例如每片 1,000 条唯一摘要。分片只用于状态管理，不代表一次 API 请求处理 1,000 篇。

执行时：

1. 从很小的 canary 并发开始；
2. 根据限流、延迟和错误率逐步增加并发；
3. 对长、短摘要分别排队，避免长请求阻塞全部队列；
4. 每次成功响应立即持久化；
5. 任何时刻都能从未完成的 record_id 继续；
6. 不因单个失败重跑整个分片；
7. 不因更改展示格式而重新调用模型。

## 11. CoT 和最终训练格式应延后生成

如果现有抽取 prompt 会产生较长 `<think>` 内容，不建议直接将它原样用于全部 18 万篇摘要。

更高效的做法是拆成两层：

1. **全量证据抽取层：** 使用同一套医学 schema 和关系约束，但只生成简洁、可验证的图谱；
2. **最终训练增强层：** 只对通过验证、去重和覆盖度选择的样本生成 CoT、教学解释或完整 LLaMAFactory assistant 内容。

这样做不是降低第一遍模型能力，而是避免为最终会被拒绝、去重或不进入训练集的文章支付大量输出 token。

如果训练目标最终不需要显式 CoT，则不应为了保持旧格式而生成 CoT。若确实需要，也必须保证 CoT 不引入摘要外医学事实。

## 12. 试验设计：先验证调用形态，再扩大规模

### 12.1 金标准样本

先建立约 300–500 篇人工复核样本，覆盖：

- PubMed、Embase 和 Cochrane；
- 短、中、长摘要；
- RCT、系统综述、观察研究、protocol 等类型；
- 明确正向结果、无显著差异、否定结果和不确定结论；
- 单一关系和多关系摘要；
- 适合抽取和应当返回空图谱的摘要。

金标准至少记录：实体、关系、证据、限定条件和是否应 abstain。

### 12.2 需要比较的运行方式

在相同金标准上比较：

- 一篇摘要一个请求；
- 每个请求打包 4 篇；
- 每个请求打包 8 篇；
- 旗舰非推理模型抽取；
- 推理模型抽取；
- 是否启用 prompt caching；
- 原始长 prompt 和压缩后的等价 prompt。

### 12.3 评价指标

不能只比较 JSON 解析成功率。至少比较：

| 指标 | 说明 |
| --- | --- |
| entity precision/recall | 实体是否准确和完整 |
| relation precision/recall | 关系是否准确和完整 |
| evidence exactness | 证据是否能精确定位并直接支持关系 |
| abstain precision/recall | 空图谱是否正确，是否漏掉可抽取文章 |
| cross-document contamination | 是否把同批其他摘要的内容混入当前记录 |
| schema-valid rate | 是否满足固定输出 contract |
| truncation rate | 是否出现响应截断 |
| input/output tokens per record | 每条记录的真实 token 成本 |
| latency and throughput | 端到端处理效率 |

batch 大小只能根据这些实测指标选择。不能因为 8 篇一请求更便宜，就在关系精度下降时仍然使用。

### 12.4 扩大顺序

建议按以下规模逐步扩大：

1. 20 条 canary：检查密钥、模型、格式和基本质量；
2. 300–500 条金标准：选择模型和 batch 方式；
3. 5,000 条生产试运行：测量真实错误率、吞吐和费用；
4. 完整唯一摘要集：开始全量主抽取；
5. 非空关系验证和空结果分层审计；
6. 争议样本裁决；
7. 最终训练集生成。

在 5,000 条阶段即可用实际 token 和非空率估算完整任务费用，不需要依赖粗略字符数猜测。

## 13. 任务状态与付费请求控制

20 万条规模必须具有 exactly-once 风格的任务状态，而不能依赖“脚本跑完一次”。

每条记录至少保存：

- record_id；
- 原始来源和重复簇；
- 输入文本哈希；
- prompt 哈希；
- schema 版本；
- 模型及 endpoint；
- 请求状态；
- 原始响应；
- 解析后的响应；
- usage/token 信息；
- 本地校验结果；
- 关系验证结果；
- 失败分类；
- 已发生的付费请求次数。

失败应分为：

1. **可本地恢复：** 字段名、代码块、Unicode 符号或轻微 JSON 包装差异；
2. **明确传输失败：** 未获得模型结果，需要进入待确认重试队列；
3. **响应截断：** 保存原始响应，只重试该 record_id；
4. **医学不确定：** 进入裁决队列，不能用相同 prompt 盲目反复请求；
5. **合法空图谱：** 正常完成，不属于失败。

默认不自动重复付费请求。先恢复已保存响应，再明确列出真正 unresolved 的 record_id，然后单独决定是否重试。

## 14. 图谱级去重与最终数据选择

处理所有摘要不代表必须把所有非空结果都放进训练集。

关系通过验证后还应进行：

- 同义实体规范化；
- 完全相同关系合并；
- 同一结论的多来源 provenance 聚合；
- 相互矛盾结论的并存和证据区分；
- 疾病、药物、关系、人群和证据等级的分布统计；
- 过度重复主题的下采样；
- 低频但重要关系的覆盖保护；
- 训练、验证和测试之间的文章及知识泄漏检查。

最终训练样本的选择标准应基于：

1. 关系已通过证据验证；
2. schema 完全合法；
3. 来源和证据可追溯；
4. 不与其他字段自相矛盾；
5. 对最终知识覆盖有增量价值；
6. 不造成严重的数据分布失衡。

## 15. 建议产物

避免为每篇文章创建一个文件。工作阶段可使用 SQLite 或分片 JSONL 保存状态，最终输出少量汇总文件：

```text
data/treatment_related_articles/
├── articles.json
├── extraction_manifest.json
├── deduplication_map.jsonl
├── frontier_extraction_raw.jsonl
├── frontier_extraction_normalized.jsonl
├── local_validation_report.json
├── relation_verification.jsonl
├── adjudication_queue.jsonl
├── verified_treatment_kg.json
├── final_training_candidates.json
└── generation_cost_and_quality_report.json
```

其中：

- `extraction_manifest.json` 固定输入、prompt、schema 和分片；
- `deduplication_map.jsonl` 保存一个唯一摘要到多个来源记录的映射；
- `frontier_extraction_raw.jsonl` 保存不可变的原始模型响应；
- `frontier_extraction_normalized.jsonl` 保存规范化图谱；
- `local_validation_report.json` 汇总结构和证据校验；
- `relation_verification.jsonl` 保存前沿模型的逐关系判定；
- `adjudication_queue.jsonl` 只包含真正有争议的样本；
- `verified_treatment_kg.json` 是通过全部验证的知识图谱；
- `final_training_candidates.json` 是去重和平衡后的训练候选；
- `generation_cost_and_quality_report.json` 记录 token、费用、错误率和质量指标。

## 16. 建议质量门槛

在进入全量处理前，建议至少满足：

| 指标 | 建议门槛 |
| --- | ---: |
| 结构化响应成功率 | ≥ 99% |
| 实体原文 span 精确匹配率 | 100% |
| 关系证据可定位率 | 100% |
| 人工抽查关系 precision | ≥ 95% |
| 空图谱高价值关系漏检率 | ≤ 5% |
| 跨文章污染率 | 0% |
| 已完成记录重复付费请求 | 0 |
| unresolved 记录可精确列出 | 100% |

如果多摘要 packing 不能达到跨文章污染率 0%，应退回一篇一请求或供应商原生 Batch API，不能为了节省 prompt token 接受数据污染。

## 17. 安全与外部数据边界

正式运行前必须确认：

1. 数据所有者允许将标题和摘要发送给所选模型服务；
2. 供应商的数据保留和日志政策可以接受；
3. API key 只从环境变量或未纳入 Git 的 `.env` 加载；
4. 原始响应和报告不能包含完整密钥；
5. endpoint、模型版本和服务商必须写入运行清单；
6. 兼容 OpenAI 请求格式不等于支持相同的缓存、Batch API 或 structured output 能力，必须分别实测。

当前参考脚本中存在明文 API key。任何新的全量任务开始前，应轮换该 key，并移除代码中的明文凭据。

## 18. 最终推荐执行顺序

1. 固定目标 KG schema、关系定义和证据要求；
2. 使用目标 tokenizer 测量全部摘要和 prompt 的真实 token；
3. 完成跨来源去重并生成稳定 record_id；
4. 建立 300–500 篇人工金标准；
5. 用前沿模型比较 1、4、8 篇每请求以及推理/非推理模式；
6. 确定质量不下降的最高效调用方式；
7. 运行 5,000 篇生产试验，估算全量费用和非空率；
8. 冻结 prompt、schema、模型和输入 manifest；
9. 前沿主模型对全部唯一摘要执行 extract-or-abstain；
10. 对全部结果进行本地严格校验和可恢复规范化；
11. 前沿验证模型检查所有候选关系；
12. 分层抽查空图谱，估计并控制漏检率；
13. 只把模型分歧和复杂歧义交给推理模型裁决；
14. 执行图谱级去重、provenance 聚合和覆盖度控制；
15. 只对最终保留样本生成 CoT 或完整训练回答；
16. 冻结最终图谱、训练集、成本报告和质量报告。

## 19. 方案结论

在以前沿模型为主的前提下，推荐方案不是“找一个便宜模型替高级模型筛文章”，也不是“让两个模型依次阅读全部 20 万篇摘要”。

推荐方案是：

> 一个前沿模型对全部唯一摘要做一次简洁、证据绑定、允许空输出的知识图谱抽取；本地程序严格检查结构和证据；另一个前沿模型只验证已经产生的关系；推理模型只裁决分歧；CoT 只为最终保留的训练样本生成。

这种设计把前沿模型能力用于真正需要医学判断的环节，同时通过去重、prompt 摊销、缓存、短输出、关系级验证和精确恢复控制 20 万条任务的成本与风险。
